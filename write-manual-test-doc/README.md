# 编写人工测试文档

> 给 QA / 开发者写一份「测什么、怎么点、该看到什么」的人工测试文档，产出 Obsidian 格式文档。

**技能名**：`write-manual-test-doc` · 目录内只有 `SKILL.md`

## 什么时候用

- 用户说「写测试文档」「人工测试文档」「QA 测试指南」
- 功能需要交给开发者/QA 按步骤手工验证时

## 怎么用

本技能不含命令，两步：

1. **加载 `dev-docs`** —— 拿到 Docs/ 的排版与结构规范，文档按其格式写。
2. **编写测试文档** —— 内容必须包含四块：
   - **测试功能清单** —— 有哪些功能需要人工测试
   - **测试流程** —— 每个功能的操作步骤（按顺序）
   - **预期结果** —— 每一步应该看到什么
   - **注意事项** —— 前置条件、环境要求、已知限制

出口：人工测试文档已生成，开发者可按文档执行测试。

> 文档落在 Docs/ 下的具体路径由 `dev-docs` 的目录规范决定，SKILL.md 未写死；详细步骤见 SKILL.md。

## 前置条件

- 待测功能与版本范围明确
- `dev-docs` 技能已安装

## 注意事项 / 已知坑

- 「测试流程」是**按顺序的操作步骤**，这是 `dev-docs` 禁序号规则的唯一例外——真步骤就该用有序列表。
- 预期结果要写到「每一步看到什么」的粒度，不能只写功能的总体期望，否则测试者无法判断单步对错。
- 前置条件、环境要求、已知限制统一放进「注意事项」，不要散落在各步骤里。
- 修完 bug 后维护这份文档用 `update-manual-test-doc`。
