# 功能盘点 → 行为文档 → 新功能设计（feature-inventory-docs-first）

> 文档先行的开发工作流：先摸清现有功能、把**当前行为**写成说明书、审计出缺口，再决定做什么并写完设计文档，最后才进入开发。

## 什么时候用

用户提出「先盘点现有功能、写文档，然后决定要做什么」时。整条链路共 6 个阶段，**顺序不可跳**——文档在前，代码在后。

## 六个阶段

| 阶段 | 做什么 | 产出 |
|---|---|---|
| 1 摸底 | 并行派 scout agent 摸客户端 / Server / 资产现状 | 功能盘点（已实现 vs 未实现/缺口清单） |
| 2 规范先行 | 写《功能文档编写规范》**让用户确认** | 经用户确认的写作规范 |
| 3 现状行为文档 | 按规范分批写行为说明书；再做深层缺口审计 | 行为说明书 + 缺陷台账 |
| 4 选功能 | 从缺口清单里挑本次开发包 | 本次开发范围 |
| 5 新功能设计文档 | 对选中的功能写**前向**设计文档，标注「待实现」 | 设计文档 |
| 6 审阅 + 定计划 | 用户审阅设计文档 → 定稿实施计划 | 实施计划 → 进入 `add-software-feature` |

## 怎么用

本技能没有命令行；提出上述诉求后按阶段推进。阶段内部的写作由被引用技能承担：

- 阶段 2、3 的写作：**排版用 `dev-docs`**，**内容流程用 `writing-functional-docs`**
- 阶段 6 之后：进入 `add-software-feature` 开发流程

> SKILL.md 未给出各阶段的具体命令、落盘目录与批次划分方式，**详细步骤见 SKILL.md**（本目录）及上述被引用技能的技能文件。

## 关键概念：两种文档不能混

- **现状行为文档**（阶段 3）：写**当前行为**——操作 / 条件 / 效果 / 边界 / 数值 / 状态字段，**禁写 API**
- **新功能设计文档**（阶段 5）：写**目标行为**而非当前行为，并标注「待实现」

## 前置条件

- 已安装 `dev-docs`、`writing-functional-docs`、`add-software-feature` 技能（本机均已装）
- 用户能参与确认：阶段 2 的规范、阶段 6 的设计文档都要用户拍板

## 注意事项 / 已知坑

- 阶段 2 的规范必须先经用户确认，否则后面分批写的文档全部要返工。
- 阶段 4 的「开发包」是从缺口清单里**选**出来的，不是全量缺口——范围由用户定。
- 阶段 6 的出口是「实施计划」，真正写代码由 `add-software-feature` 承接，本技能不含实现步骤。
- SKILL.md 仅 29 行，是阶段骨架而非可执行手册。
